# Course Workspace

Course Workspace reuses the existing `CourseOffering` record. It does not create
a second course catalogue or duplicate enrollment model.

## URLs and access

| User | URL | Access rule |
|---|---|---|
| Teacher/admin | `/teacher/courses/{offering_id}` | Assigned teacher, approved assignment, valid provider/creator, or super admin |
| Student/CR | `/student/courses/{offering_id}` | Active enrollment in the published offering and active semester |
| Notification alias | `/course-offerings/{offering_id}/workspace` | Same backend authorization as the caller's role |

The frontend hides unavailable workspaces, but the backend remains authoritative.
Guessing an offering ID does not bypass the offering, enrollment, or teacher
scope checks.

## Workspace tabs

- **Overview** — course/semester status, teachers, active enrollment count,
  announcements, schedule entries, events, questions, and quick actions.
- **Announcements** — draft, scheduled, published, pinned, archived, search,
  filters, pagination, read state, and audience-aware feeds.
- **Resources** — course-scoped files, authenticated presigned downloads, and
  teacher upload/publish/unpublish/archive controls.
- **Assignments** — links to existing academic work; no duplicate assignment
  model is invented where the repository has no course assignment entity.
- **Events** — classes, quizzes, exams, vivas, deadlines, lab exams,
  presentations, holidays, and other course events.
- **Attendance** and **Schedule** — links to existing offering-scoped academic
  views rather than duplicate schedule or attendance data.
- **Questions** — enrolled students ask moderated questions; course staff answer
  or resolve them.
- **Students** — staff-only active roster; learners see only the aggregate count.
- **Settings** — read-only offering details and server-returned permissions.

## Announcement lifecycle

Announcements are plain text; HTML, scripts, embedded objects, and unsafe markup
are stripped before storage. Supported types are `general`, `class_update`,
`class_cancelled`, `exam`, `assignment`, `urgent`, `resource`, and
`administrative`. Supported audiences are `enrolled_students`, `cr_only`, and
`teachers_only`; unsupported selected-user targeting is rejected rather than
stored without a safe recipient model.

| Status | Meaning |
|---|---|
| `draft` | Staff-only editable content; no notification |
| `scheduled` | Future `publish_at`; hidden from learners until Celery publishes it |
| `published` | Visible to the selected audience and notification-eligible |
| `archived` | Removed from the learner feed; cannot be edited or republished |

Publishing creates one deterministic durable notification per eligible recipient.
Urgent announcements use high priority; normal announcements use the existing
medium/digest path. Notification preferences, quiet hours, push opt-out, and
in-app settings are respected. Repeated publish/retry does not duplicate inbox
rows because the `(user_id, event_id, type)` outbox key is unique. In-app links
are generated by the server and point to the workspace announcement query; no
caller-provided URL is accepted.

## Resource rules

Resources reuse `AcademicResource` and the existing MinIO/S3 presigned upload
service. `CourseResource` stores offering-specific publication/archive state.
Allowed files remain the existing PDF, office, ZIP, PNG, and JPEG set with the
25 MB limit, extension/MIME checks, sanitized storage keys, ownership validation,
short-lived upload/download URLs, and authenticated course scope.

Teacher endpoints:

```text
POST  /api/v1/course-offerings/{offering_id}/resources/presigned-upload
POST  /api/v1/course-offerings/{offering_id}/resources/finalize
PATCH /api/v1/course-offerings/{offering_id}/resources/{resource_id}
```

Students see only published, non-archived resources for their active enrollment.

## Events and questions

Course events use `CourseEvent` and are published by default when created by
authorized staff. They are scoped to the offering, support optional location,
end time, and reminder minutes, and can be archived. Celery scans upcoming
published events and creates one deterministic `exam_reminder` notification per
active enrolled student; the normal notification preference and outbox rules
still apply.

Course questions use `CourseQuestion`. Students can ask only in an active
enrolled course. Course-visible questions are visible to the course staff and
enrolled learners; private questions are visible to the student and staff only.
Teachers/admins can answer, resolve, or close questions. Answers are plain text,
rate-limited, and notify the question owner through the existing durable
notification system.

## API surface

```text
GET    /api/v1/course-offerings/{offering_id}/workspace
GET    /api/v1/student/course-offerings/{offering_id}/workspace
GET    /api/v1/course-offerings/{offering_id}/announcements
POST   /api/v1/course-offerings/{offering_id}/announcements
PATCH  /api/v1/course-offerings/{offering_id}/announcements/{announcement_id}
POST   /api/v1/course-offerings/{offering_id}/announcements/{announcement_id}/publish
POST   /api/v1/course-offerings/{offering_id}/announcements/{announcement_id}/archive
PATCH  /api/v1/course-offerings/{offering_id}/announcements/{announcement_id}/pin
PATCH  /api/v1/course-announcements/{announcement_id}/read
GET    /api/v1/course-offerings/{offering_id}/resources
GET    /api/v1/course-offerings/{offering_id}/events
POST   /api/v1/course-offerings/{offering_id}/events
PATCH  /api/v1/course-offerings/{offering_id}/events/{event_id}
POST   /api/v1/course-offerings/{offering_id}/events/{event_id}/archive
GET    /api/v1/course-offerings/{offering_id}/questions
POST   /api/v1/course-offerings/{offering_id}/questions
PATCH  /api/v1/course-offerings/{offering_id}/questions/{question_id}/answer
```

The `20261012_0012_course_workspace` Alembic revision creates announcements,
read state, offering-resource state, events, and questions. It is applied by the
normal one-shot `migrate` service before the API and workers start.
